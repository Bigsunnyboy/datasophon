# 现有组件服务定义扩展规范

## 1. 概述

本文档定义了DataSophon服务定义文件（service_ddl.json）的扩展规范，以支持现有组件的接入与托管功能。扩展设计遵循**向后兼容**原则，新增字段不会影响现有安装流程。

## 2. 扩展字段说明

### 2.1 根级别扩展字段

在现有service_ddl.json的根级别添加以下字段：

| 字段名 | 类型 | 必填 | 默认值 | 描述 |
|--------|------|------|--------|------|
| `installationType` | `string` | 否 | `"new"` | 安装类型：`"new"`（全新安装）、`"existing"`（现有组件）、`"mixed"`（混合模式） |
| `existingComponentSupport` | `object` | 否 | `null` | 现有组件支持配置，当`installationType`为`"existing"`或`"mixed"`时生效 |

### 2.2 existingComponentSupport对象结构

```json
{
  "existingComponentSupport": {
    "enabled": true,
    "detectionMethods": [...],
    "validationRules": [...],
    "configManagement": {...},
    "takeoverCapabilities": [...],
    "compatibilityMatrix": {...}
  }
}
```

#### 2.2.1 enabled字段
- **类型**: `boolean`
- **默认值**: `true`
- **描述**: 是否启用现有组件支持

#### 2.2.2 detectionMethods字段
检测现有组件的方法列表，按优先级顺序执行：

```json
"detectionMethods": [
  {
    "type": "port_check",
    "port": 50070,
    "path": "/jmx",
    "protocol": "http",
    "timeout": 10,
    "description": "通过HTTP端口检测"
  },
  {
    "type": "process_pattern", 
    "pattern": "NameNode|DataNode|JournalNode",
    "user": "hdfs",
    "command": "ps aux",
    "description": "通过进程名检测"
  },
  {
    "type": "config_file",
    "path": "/etc/hadoop/conf/hdfs-site.xml",
    "keys": ["dfs.namenode.http-address", "dfs.namenode.name.dir"],
    "format": "xml",
    "description": "通过配置文件检测"
  },
  {
    "type": "command",
    "command": "which hdfs",
    "expectedOutput": "/usr/bin/hdfs",
    "description": "通过命令行工具检测"
  },
  {
    "type": "api",
    "url": "http://${host}:8088/ws/v1/cluster/info",
    "method": "GET",
    "expectedKeys": ["clusterInfo.clusterId"],
    "description": "通过REST API检测"
  }
]
```

##### 检测方法类型说明：
- **port_check**: 端口检查，检测指定端口是否开放
- **process_pattern**: 进程模式匹配，通过进程名检测
- **config_file**: 配置文件解析，读取配置文件中的关键值
- **command**: 命令执行，执行命令并检查输出
- **api**: API调用，调用REST API并验证响应

#### 2.2.3 validationRules字段
验证组件可用性的规则列表：

```json
"validationRules": [
  {
    "type": "connectivity",
    "target": "${host}:${port}",
    "timeout": 30,
    "description": "检查服务连通性"
  },
  {
    "type": "functional",
    "command": "hdfs dfsadmin -report",
    "expectedPattern": "Live datanodes",
    "timeout": 60,
    "description": "验证HDFS功能"
  },
  {
    "type": "performance", 
    "operation": "read",
    "testFile": "/test.dat",
    "size": "1MB",
    "maxLatency": 1000,
    "description": "性能基准测试"
  },
  {
    "type": "security",
    "check": "kerberos_enabled",
    "expected": false,
    "description": "安全配置检查"
  }
]
```

##### 验证规则类型说明：
- **connectivity**: 连通性验证（TCP/HTTP）
- **functional**: 功能性验证（执行特定操作）
- **performance**: 性能验证（基准测试）
- **security**: 安全性验证（安全配置检查）

#### 2.2.4 configManagement字段
配置管理相关设置：

```json
"configManagement": {
  "mergeStrategy": "smart_merge",
  "backupBeforeChange": true,
  "backupRetention": 7,
  "conflictResolution": "priority_existing",
  "excludedKeys": [
    "dfs.encryption.key",
    "dfs.https.keystore.password",
    "yarn.resourcemanager.keytab"
  ],
  "sensitiveKeys": [
    "*.password",
    "*.secret",
    "*.keytab",
    "*.keystore"
  ],
  "autoSync": {
    "enabled": false,
    "interval": 300,
    "direction": "to_datasophon"
  }
}
```

##### 合并策略说明：
- **preserve**: 完全保留现有配置，不应用DataSophon模板
- **override**: 完全使用DataSophon模板配置，覆盖现有配置
- **smart_merge**: 智能合并（推荐）
  - 安全相关配置：保留现有值
  - 性能相关配置：取优化值
  - 服务端点配置：保留现有值
  - 新增配置项：添加DataSophon推荐值

##### 冲突解决策略：
- **priority_existing**: 优先使用现有配置（生产安全）
- **priority_datasophon**: 优先使用DataSophon配置（标准化）
- **manual**: 需要人工确认

### 2.3 角色级别扩展字段

在`roles`数组的每个角色对象中，可以添加以下扩展字段：

```json
{
  "name": "NameNode",
  "existingComponentConfig": {
    "detectionOverride": {...},
    "validationOverride": [...],
    "configOverride": {...}
  }
}
```

#### 2.3.1 detectionOverride字段
角色特定的检测方法覆盖，优先级高于全局配置。

#### 2.3.2 validationOverride字段
角色特定的验证规则覆盖。

#### 2.3.3 configOverride字段
角色特定的配置管理覆盖。

## 4. 向后兼容性

### 4.1 现有服务定义兼容性
- 没有`installationType`字段的服务定义默认为`"new"`（全新安装模式）
- 没有`existingComponentSupport`字段的服务定义不支持现有组件接入
- 新增字段不会影响现有安装流程的解析和执行

### 4.2 加载器兼容性
现有的`LoadServiceMeta`类需要扩展以支持新字段：

```java
public class ServiceInfo {
    // 原有字段
    private String name;
    private String label;
    private String version;
    private List<ServiceRoleInfo> roles;
    // ...
    
    // 新增字段
    private String installationType = "new";
    private ExistingComponentConfig existingComponentConfig;
    
    // 新增方法
    public boolean supportsExistingComponent() {
        return existingComponentConfig != null && existingComponentConfig.isEnabled();
    }
    
    public boolean isExistingComponentMode() {
        return "existing".equals(installationType) || "mixed".equals(installationType);
    }
}
```

### 4.3 安装流程兼容性
当检测到`installationType`为`"existing"`时：
1. 跳过软件包下载和安装步骤
2. 执行组件发现和验证
3. 执行配置提取和合并
4. 注册服务实例到DataSophon

当`installationType`为`"mixed"`时：
1. 先尝试发现现有组件
2. 对于未发现的组件执行全新安装
3. 统一注册和管理

## 5. 扩展点实现

### 5.1 新增Java类

需要新增以下Java类来支持扩展字段：

1. **ExistingComponentConfig.java** - 现有组件支持配置
2. **DetectionMethod.java** - 检测方法定义
3. **ValidationRule.java** - 验证规则定义  
4. **TakeoverCapability.java** - 接管能力定义
5. **CompatibilityMatrix.java** - 兼容性矩阵定义

### 5.2 JSON解析扩展

扩展`LoadServiceMeta`类的解析逻辑：

```java
public class ExtendedServiceMetaParser {
    
    public ServiceInfo parse(String jsonContent) {
        ServiceInfo serviceInfo = originalParser.parse(jsonContent);
        
        // 解析扩展字段
        JsonNode rootNode = objectMapper.readTree(jsonContent);
        
        if (rootNode.has("installationType")) {
            serviceInfo.setInstallationType(rootNode.get("installationType").asText("new"));
        }
        
        if (rootNode.has("existingComponentSupport")) {
            JsonNode existingSupportNode = rootNode.get("existingComponentSupport");
            ExistingComponentConfig config = parseExistingComponentConfig(existingSupportNode);
            serviceInfo.setExistingComponentConfig(config);
        }
        
        return serviceInfo;
    }
    
    private ExistingComponentConfig parseExistingComponentConfig(JsonNode node) {
        ExistingComponentConfig config = new ExistingComponentConfig();
        
        if (node.has("enabled")) {
            config.setEnabled(node.get("enabled").asBoolean(true));
        }
        
        if (node.has("detectionMethods")) {
            List<DetectionMethod> methods = parseDetectionMethods(node.get("detectionMethods"));
            config.setDetectionMethods(methods);
        }
        
        // 解析其他字段...
        
        return config;
    }
}
```

### 6.2 运行时验证
在服务加载时进行验证：

```java
public class ServiceDefinitionValidator {
    
    public ValidationResult validate(ServiceInfo serviceInfo) {
        List<String> errors = new ArrayList<>();
        
        // 验证installationType
        if (!isValidInstallationType(serviceInfo.getInstallationType())) {
            errors.add("Invalid installationType: " + serviceInfo.getInstallationType());
        }
        
        // 验证现有组件配置
        if (serviceInfo.getExistingComponentConfig() != null) {
            ValidationResult configValidation = 
                validateExistingComponentConfig(serviceInfo.getExistingComponentConfig());
            if (!configValidation.isValid()) {
                errors.addAll(configValidation.getErrors());
            }
        }
        
        // 验证角色级别的覆盖配置
        for (ServiceRoleInfo role : serviceInfo.getRoles()) {
            if (role.getExistingComponentConfig() != null) {
                ValidationResult roleValidation = 
                    validateRoleConfig(role.getExistingComponentConfig());
                if (!roleValidation.isValid()) {
                    errors.add("Role " + role.getName() + ": " + roleValidation.getErrors());
                }
            }
        }
        
        return errors.isEmpty() ? 
            ValidationResult.valid() : 
            ValidationResult.invalid(errors);
    }
}
```

## 7. 迁移指南

### 7.1 现有服务定义迁移
对于已有的服务定义文件，可以通过以下步骤添加现有组件支持：

1. 在根级别添加`installationType`字段
2. 添加`existingComponentSupport`对象
3. 根据组件特性配置检测方法和验证规则
4. 测试扩展后的定义文件

## 8. 最佳实践

### 8.1 配置设计原则
1. **渐进式能力**：从Level 1（监控）开始，逐步开放更高级别能力
2. **安全优先**：默认保留现有安全配置，不覆盖敏感信息
3. **明确兼容性**：清晰定义支持的版本和功能限制
4. **详细验证**：设计全面的验证规则确保组件可用性

### 8.2 检测方法设计
1. **多方法冗余**：配置多种检测方法提高发现成功率
2. **优先级排序**：将快速、可靠的方法放在前面
3. **环境适应性**：考虑不同部署环境的差异
4. **故障隔离**：单个检测方法失败不应影响整体流程

### 8.3 验证规则设计
1. **分层验证**：连通性→功能性→性能→安全性
2. **超时控制**：设置合理的超时时间避免长时间阻塞
3. **清理机制**：测试产生的临时数据需要清理
4. **结果缓存**：验证结果可以缓存避免重复验证

## 9. 常见问题解答

### 9.1 Q: 如何为已有服务添加现有组件支持？
A: 在service_ddl.json根级别添加`installationType`和`existingComponentSupport`字段，参考第3节示例。

### 9.2 Q: 现有组件支持会影响全新安装吗？
A: 不会。当`installationType`为`"new"`或未设置时，按原有流程执行全新安装。

### 9.3 Q: 如何控制接管程度？
A: 通过`takeoverCapabilities`配置不同级别的能力，实际接管时可以选择从哪个级别开始。

### 9.4 Q: 配置合并冲突如何解决？
A: 通过`configManagement.conflictResolution`配置冲突解决策略，支持优先现有配置、优先DataSophon配置或人工确认。

### 9.5 Q: 如何测试扩展后的服务定义？
A: 可以使用提供的验证工具检查JSON格式，然后在测试环境执行组件发现和接管流程。
